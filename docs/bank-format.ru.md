# ConstraintLab: модель анализа и формат банка задач

Документ для авторов задач и разработчиков. Как пользоваться программой – в [README.ru.md](../README.ru.md);
правила оформления задач – в [authoring-guide.md](authoring-guide.md), термины – в [terminology.md](terminology.md).

## Что моделирует ConstraintLab

- Интерпретатор подмножества Tcl 8.6 (`set`, `expr` с целочисленным делением как в Tcl, списки,
  `foreach`, `if`, `proc`, `format` и др.). В режиме XDC выдаётся предупреждение о командах,
  которые Vivado не допускает в управляемом XDC-файле.
- Объекты: порты, ячейки (включая иерархические), выводы, цепи, тактовые сигналы; шаблоны,
  `-hierarchical`, `-regexp`, `-filter`, `-of_objects`, `all_*`, коллекции.
- Тактовые сигналы: первичные, виртуальные, производные (`-divide_by`, `-multiply_by`, `-edges`,
  `-edge_shift`, `-invert`, `-duty_cycle`, `-combinational`, `-add`, `-master_clock`),
  автоматически выводимые тактовые сигналы MMCM/PLL/BUFR/BUFGCE_DIV (режим Vivado),
  переименование автоматически выведенных сигналов, блокировка исходного сигнала в точке
  определения производного, распространение через буферы, мультиплексоры и логику,
  `set_case_analysis`, `set_disable_timing`.
- Пути: от входных портов и регистров к выходным портам и информационным (в том числе
  асинхронным) входам регистров; DDR-примитивы IDDR и ODDR; условные проверки библиотеки
  (вход SI сканируемого триггера проверяется только при SE = 1, вход D – при SE = 0).
- Сравнение с эталоном – по смыслу: нестрогие проверки DDR-интерфейсов (они никогда не бывают
  худшими) можно исключать или оставлять, равноценные записи (`-to` на ячейку или на её вывод D,
  `set_driving_cell` с `-pin` и без) засчитываются одинаково.
- Требования к предустановке и удержанию по фронтам тактовых сигналов на общем периоде,
  многотактные пути (`-setup/-hold`, `-start/-end`), ложные пути, `set_max_delay`
  (в том числе `-datapath_only`), `set_min_delay`, группы тактовых сигналов, приоритеты
  исключений; задержки ввода/вывода с правильной семантикой `-add_delay`.
- Физические свойства XDC (`set_property`, `-dict`), окружение ASIC (`set_load`,
  `set_driving_cell`, `set_clock_uncertainty`/`latency`/`transition` и др.).

**Ограничение модели:** тактовые сигналы идеальные, задержки ячеек и трассировки не считаются.
ConstraintLab проверяет смысл ограничений – какие требования из них следуют, – а не запас конкретной
реализации. Окончательная проверка выполняется в Vivado или PrimeTime (`report_timing_summary`,
`check_timing`, `report_exceptions`, `report_clock_interaction`).

## Как добавить задачу

Задачи хранятся в каталоге `bank/`. Каждый файл подключается в `bank/index.js`:

```js
XT.BANK_FILES = [
  '01_clocks.js',
  '50_my.js',        // ваш файл
];
```

Можно также воспользоваться меню ⋮ → **«Режим автора»**: там есть шаблон, проверка задачи,
предварительный просмотр и сохранение в «мой банк» (в браузере) или в файл `.js`.
Готовый файл можно передать другим через меню ⋮ → «Импорт пакета задач».

Проверка всего банка в консоли (нужен Node.js):

```bash
node tools/validate.js            # краткий отчёт
node tools/validate.js -v         # подробно
node tools/validate.js clocks.    # только задачи с id, содержащим «clocks.»
```

Валидатор строит проект, отрисовывает рисунки, проверяет, что эталон проходит собственную
проверку, а тесты дают ожидаемый результат, и ищет длинные тире в текстах.

### Модуль

```js
XT.bank.module({ id: 'my', order: 50, title: '50. Мои задачи', about: 'краткое описание' });
```

### Вопрос

```js
XT.bank.add({
  id: 'my.adc_in',            // уникальный идентификатор
  module: 'my',               // модуль
  order: 1,                   // порядок в модуле
  title: 'Вход АЦП',          // заголовок
  tool: 'vivado',             // схема и проверка: 'vivado' (примитивы ПЛИС) или 'sdc' (ячейки ASIC)
  lang: 'both',               // где применимо решение: 'both' (XDC и SDC), 'xdc' или 'sdc'
  langNote: '…',              // чем отличаются XDC и SDC в этой задаче (показывается в разборе)
  type: 'sdc',                // 'sdc' (написать ограничения), 'choice' (выбор), 'numeric' (расчёт)
  level: 2,                   // сложность 1..3
  tags: ['set_input_delay'],
  text: `Условие в Markdown.`,
  design: { elements: [...], wires: [...] },   // проект: и схема, и список соединений
  figures: [ ... ],           // дополнительные рисунки (временны́е диаграммы, схемы)
  given: `...`,               // ограничения проекта ДО кода пользователя (показываются)
  after: `...`,               // ограничения проекта ПОСЛЕ кода пользователя (ссылаются на его объекты)
  starter: `...`,             // начальный текст редактора (например, код с ошибками)
  solution: `...`,            // эталон
  solutions: [`...`, `...`],  // вместо solution: несколько равноценных эталонов
  check: { ... },             // настройка проверки (см. ниже)
  hints: ['…', '…'],          // подсказки по возрастанию подробности
  explain: `Разбор в Markdown`,
  refs: 'UG903, глава «Constraining I/O Delay»',
  tests: [                    // самопроверка задачи (используется валидатором)
    { code: '…', pass: true,  note: 'равноценная запись' },
    { code: '…', pass: false, note: 'типичная ошибка', expect: 'регулярное выражение для текста диагностики' },
  ],
});
```

Для `type: 'choice'`: `options: [{ text, ok: true, why }]`, `multi: true` – несколько верных.
Для `type: 'numeric'`: `fields: [{ label, answer, tol, unit }]`.

### Проект (design)

Описание проекта одновременно задаёт схему (координаты в пикселях) и список соединений
для анализа. Элемент:

```js
{ id: 'r', t: 'ff', name: 'data_reg', w: 8, x: 300, y: 40 }
```

| `t` | Примитив | Выводы | Примечание |
|---|---|---|---|
| `in`, `out`, `inout` | порт | `pad` (снаружи), внутренняя сторона без имени | `w` – разрядность шины, `lsb`; `flip: true` – площадка с другой стороны |
| `ff` | FDRE | C, D, CE, R, Q | `negedge: true` – по спаду; `ce: true`, `rst: 'R'` – показать выводы |
| `fdce`, `fdpe`, `fdse` | FDCE/FDPE/FDSE | CLR/PRE – асинхронные | |
| `iddr` | IDDR | C, D, Q1, Q2 | захват по фронту и спаду |
| `oddr` | ODDR | C, D1, D2, Q | запуск по фронту и спаду |
| `ibuf`, `obuf`, `ibufds`, `obufds`, `iobuf`, `obuft` | буферы ввода/вывода | I, O, IB, OB, IO, T | |
| `idelay` | IDELAYE2 | IDATAIN, DATAOUT | |
| `bufg`, `bufh`, `bufio`, `bufgce`, `bufgmux`, `bufr`, `bufgce_div` | тактовые буферы | I, O, CE, I0, I1, S | `attrs: { BUFR_DIVIDE: 4 }` |
| `mmcm`, `pll` | MMCME2_ADV, PLLE2_ADV | CLKIN1, CLKOUT0…6 | `mult`, `divclk`, `outs: [{ pin, div, phase, duty, clk, label }]` |
| `logic` | комбинационная логика | I (I0…I3 для рисунка), O | `label`, `mix: true` – каждый выход зависит от всех входов |
| `ram` | RAMB36E1 | ADDRARDADDR, DIADI, WEA, CLKARDCLK, DOADO | |
| `block` | произвольный блок | `pins: [{ n, d, w, clk, side }]` | `timing: { seq, clk, launch, capture, async, arcs }` |
| `dff`, `dffn`, `dffr`, `sdff`, `sdffr` | триггеры ASIC | CK, D, Q, RN, SI, SE | у сканируемых проверки D действуют при SE = 0, SI – при SE = 1 |
| `buf`, `inv`, `and2`, `or2`, `nand2`, `nor2`, `xor2`, `mux2`, `ckmux2`, `icg`, `apll` | ячейки ASIC | A, B, S, Y, CK, E, GCK, REFCLK | |
| `vcc`, `gnd` | константы | P, G | |
| `chip`, `osc`, `conn` | внешние устройства (только рисунок) | `pins: [{ n, side, y }]` | `ext: true`; в `title` можно перенос строки `\n` |
| `boundary`, `note`, `label` | граница кристалла, примечание, надпись | | граница подгоняется автоматически |

Общие поля: `name` (имя экземпляра, `%` – номер разряда), `w` (число экземпляров/разрядов),
`noName`, `nameX`/`nameY` (смещение подписи имени), `tag`, `attrs`, `props` (начальные свойства),
`hidden` (в анализе есть, на рисунке нет), `ext` (только рисунок).

Провод:

```js
{ from: 'bg.O', to: ['r1.C', 'r2.C'], kind: 'clk', label: 'sys_clk', net: 'sys_clk_g' }
```

`kind`: `clk` (тактовый, оранжевый), `rst`, `ext` (вне кристалла, пунктир), по умолчанию –
данные. Разрядности согласуются автоматически: шина → шина поразрядно, один разряд → шина
веером. Трассировка: `mx` – абсцисса вертикального участка, `my` – ордината обхода,
`via: [[x, y], …]` – промежуточные точки, `trunk` – отступ общего ствола при разветвлении,
`lx`/`ly` – положение подписи. Отдельные разряды многоразрядного элемента или порта выбирают
в имени: `{ from: 'rc[0:6].Q', to: 'rc[1:7].SI' }` (цепочка сканирования), `{ from: 'psel[1]', to: 'mux.S' }`.
Точки соединения ставятся автоматически там, где провода одной цепи
сходятся в трёх и более направлениях. Косая черта с разрядностью шины ставится сама на свободный
участок (не у точки соединения); `noSlash: true` её убирает.

### Временна́я диаграмма

```js
{
  kind: 'timing', title: 'Окно данных', t: [-2, 22],          // диапазон времени, нс
  signals: [
    { name: 'clk', clock: { period: 10, rise: 0, fall: 5, jitter: 0.2 }, arrows: 'rise' },
    { name: 'data', bus: [[1.2, 3.1, 'D0'], [11.2, 13.1, 'D1']], init: 'X' }, // [от, до, значение]
    { name: 'valid', bit: [[2, 2.4, 1], [12, 12.4, 0]], init: 0 },
  ],
  marks:   [{ t: 0, label: 'запуск', cls: 'launch' }],              // вертикальные метки
  spans:   [{ row: 'data', t0: 0, t1: 3.1, label: 'Tco max', cls: 'data' }], // размерные стрелки
           // (lt: 1.5, anchor: 'start' – задать положение подписи вручную)
  windows: [{ row: 'data', t0: 8, t1: 10, label: 'tsu', cls: 'setup' }],    // закрашенные окна
  arrows:  [{ from: [0, 'clk', 'mid'], to: [3.1, 'data', 'mid'], label: '…' }],
  caption: 'подпись под рисунком',
}
```

Поддерживается и подмножество WaveJSON (WaveDrom): `{ kind: 'wave', wave: { signal: [...], edge: [...] } }`.

### Настройка проверки (check)

| Поле | Смысл |
|---|---|
| `clockNames: true` или `['имя']` | требовать точные имена тактовых сигналов |
| `requireVirtual: true` | требовать виртуальный тактовый сигнал |
| `layers: ['clocks', 'io', 'paths', 'props', 'misc']` | сравнивать только указанные слои |
| `strictProps: true` | лишние свойства считать ошибкой |
| `allowProps: { порт: { СВОЙСТВО: значение } }` | лишние свойства, допустимые только с этим значением (например, N-вывод дифференциальной пары) |
| `require: [{ cmd, opt, msg }]` | обязательная команда (с опцией) |
| `forbid: [{ cmd, opt, msg }]` | запрещённая команда |

## Терминология

Тексты задач и сообщений пишутся научно-техническим русским языком без жаргона
(см. [terminology.md](terminology.md)): «тактовый сигнал», а не «клок»; «ограничения», а не «констрейнты»;
«вывод», а не «пин»; «коэффициент заполнения», а не «скважность» в смысле duty cycle.
Длинное тире не используется – только «–» или «-».

```
js/sdc.js           – команды XDC/SDC
js/sta.js           – тактовые сигналы, пути, соотношения фронтов, исключения
js/checker.js       – сравнение с эталоном и диагностика
js/reports.js       – отчёты консоли
js/schematic.js     – построение схем
js/wave.js          – временны́е диаграммы
js/md.js, editor.js – Markdown, подсветка, редактор
js/refdocs.js       – справочник
js/app.js           – интерфейс
bank/               – банк задач
tools/validate.js   – проверка банка (Node.js)
tools/test-engine.js – регрессионные тесты движка (Node.js)
tools/screenshot.js – снимки интерфейса в Chrome без окна (для авторов задач)
tools/build.py      – сборка в один HTML-файл
tools/dev/q.js      – проверка одного вопроса из консоли: вердикт и вывод команд
                      (node tools/dev/q.js 10_asic.js asic.test_mux @ref "check_timing")

tools/dev/smoke.json – сквозная проверка всех вопросов в браузере (через tools/screenshot.js)
run.sh, run.bat     – запуск в отдельном окне (режим приложения Chrome/Edge)
docs/               – глоссарий и руководство автора задач
```
